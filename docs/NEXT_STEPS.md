### 1. 입찰 요청을 현재 경매에 묶기

대상: `packages/shared/src/index.ts`, `apps/server/src/game-engine.ts`, `apps/server/src/auction-room.ts`, `apps/web/src/App.vue`, 기존 엔진·소켓 테스트.

**변경 전 근거:** 입찰 메시지가 `{ amount }`만 전달해 어떤 경매의 요청인지 구분하지 못했다. 읽기 전용 엔진 확인에서 1라운드용 금액 요청을 2라운드에 전달했을 때 승인되는 동작을 확인했다. 실제 네트워크 지연이 발생한 운영 사례를 재현한 것은 아니다.

- [x] 서버가 각 경매에 `auctionId`를 발급하고 공개 스냅샷에 포함한다. 재경기를 포함해 경매마다 새 UUID를 발급한다.
- [x] 사용자가 입찰 버튼을 누를 때 화면에 표시된 `auctionId`와 금액을 함께 보낸다.
- [x] 서버에서 누락·잘못된 자료형·현재 경매와 불일치하는 ID를 거절하고, 입찰·잔액·기록을 변경하지 않는다.
- [x] 오래된 경매 요청이 거절되면 현재 물건과 입찰가를 다시 확인하도록 안내한다. 새 물건에 자동으로 재입찰하지 않는다.
- [x] 봇의 내부 입찰 경로와 기존 테스트 호출부도 변경된 계약에 맞춘다.
- [x] 이전 라운드, 재경기 이전 게임, 누락 ID, 정상 ID를 엔진과 실제 SDK 테스트로 검증한다.

**완료 기준:** 정상 경매의 입찰·낙찰은 그대로 동작하고, 이전 경매의 요청은 다음 경매 상태를 바꾸지 못한다. 프런트엔드와 서버를 함께 갱신하는 메시지 계약 변경임을 문서에 기록한다.

**완료 기록 (2026-09-26):** 입찰 계약은 `BidRequest { auctionId: string, amount: number }`이며, 이전 `{ amount }` 클라이언트와 호환되지 않으므로 프런트엔드와 서버를 함께 갱신한다. 스냅샷의 ID는 대기실·최종 결과에서 `null`, 낙찰 공개 중에는 직전 경매 ID다. 유효한 입찰 시간 안에서 누락·비문자열·빈 ID는 `INVALID_AUCTION_ID`, 다른 ID는 `STALE_AUCTION`으로 거절한다. 엔진 19개·소켓 6개, Chromium·WebKit E2E 6개와 개발 모드 2개, 타입·빌드·형식 검사를 통과했다. 오래된 요청은 엔진·SDK에서 직접 주입해 검증했으며 실제 네트워크 지연이나 실제 휴대폰 검증으로 해석하지 않는다.

### 3. 연결·입력·퇴장 경계 상황 보강

대상: `apps/server/src/auction-room.ts`, `apps/server/src/game-engine.ts`, `apps/web/src/composables/useGame.ts`, 기존 엔진·소켓·브라우저 테스트.

재접속과 방장 이전은 이미 구현되어 있다. 새로 만드는 작업보다 현재 동작의 미확인 경계를 확인하고 실패 안내를 다듬는 데 집중한다.

- [ ] 자동 재접속 중에는 중복 참가·수동 재접속·입찰이 실행되지 않는지 확인한다.
- [ ] 30초 이내 복귀와 유예 만료 후 복귀 실패를 각각 확인한다. 만료·서버 재시작 시 이전 방에 갇히지 않고 새 방 입장으로 이어지게 한다.
- [ ] 방장의 명시적 퇴장, 갑작스러운 연결 종료, 전원 퇴장, 게임 종료 직전 퇴장을 실제 소켓으로 확인한다.
- [ ] 입찰 직후 연결이 끊겨도 재접속한 스냅샷이 서버의 실제 입찰·잔액·낙찰 결과와 일치하는지 확인한다.
- [ ] `sync`, `ready`, `bid`, `reaction` 등 메시지의 예상하지 못한 자료형·반복 전송을 점검한다. 거부된 요청으로 게임 상태가 바뀌지 않게 한다.
- [ ] 새 게임·새 방 전환 시 이전 오류, 반응 이모지, 입찰 대기 표시, 비밀 미션 표시 상태가 남는지 확인한다.

**완료 기준:** 잘못된 요청이나 연결 실패가 다른 참가자의 게임을 멈추지 않는다. 중복 차감·중복 지급·타인의 비밀 미션 노출이 없고, 복귀 불가 상태에서는 이유와 다음 행동을 표시한다. 새로 발견한 실패에 대해서만 재현 테스트를 추가한다.

대상: `packages/shared/src/index.ts`, `apps/server/src/game-engine.ts`, `apps/web/src/App.vue`, `ItemArt.vue` 및 분리된 화면 컴포넌트.

- [ ] 3인과 5~6인 상황에서 각각 플레이한다. 합계 6판 이상을 첫 관찰 목표로 삼고, 이를 통계적인 균형 검증으로 해석하지 않는다.
- [ ] 라운드별 낙찰가·입찰 참여자 수·유찰 수, 미션 종류·성공 여부, 최종 순위, 입찰 없이 기다린 구간과 다시 하고 싶은지를 기록한다.
- [ ] 특정 물건 미션 +60점, 물건 2개 미션 +50점, 절약 미션 +45점이 참가 인원과 입찰 순서에 따라 어떻게 작용하는지 살핀다. 특정 미션이 유리하다는 결론은 플레이 기록 이후에 내린다.
- [ ] 서로 다른 물건 수집 미션 배정이 경쟁을 약하게 하는지, 아무것도 사지 않고 남긴 100점이 적극적인 입찰보다 유리하게 작용하는지 가설로 검토한다.
- [ ] 25초가 길거나 짧게 느껴지는지, 4초 낙찰 공개를 읽을 수 있는지 확인한 뒤 시간 또는 정보량을 조정한다.
- [ ] 반응이 약한 장면부터 낙찰 도장·입찰 피드백·결과 공개 연출을 보강한다. 효과음을 추가한다면 음소거와 사용자 조작 이후 재생을 함께 제공한다.
- [x] 사용자 요청으로 물건을 30종으로 확장하고 매 게임에는 5종만 무작위 출품한다. 수집 미션 목표가 출품되지 않을 수 있는 규칙과 안내를 적용한다.
- [ ] 목표 물건의 미출품 빈도와 수집 미션·일반 미션의 배정 비율이 재미에 미치는 영향을 플레이 기록으로 확인한다. 목표 미출품을 허용하는 현재 규칙을 기준으로 검토한다.

**완료 기준:** 각 변경에 관찰 근거와 전후 비교 기록이 있다. 규칙 변경 시 점수 계산·미션 달성·재경기 초기화 테스트를 갱신하고, 기존의 서버 검증과 미션 비공개 원칙을 유지한다.

### 5. CI와 소규모 운영 준비

대상: 신규 `.github/workflows/ci.yml`, `apps/server/src/app.ts`, `apps/server/src/auction-room.ts`, `apps/server/src/index.ts`, 환경 예시·운영 문서.

현재 확인된 범위에서 CI 워크플로 파일은 없다. `/health`, WebSocket 최대 payload 4KB, 메시지 초당 40개 제한, 리액션 800ms 간격 제한, ping, 종료 시그널 처리는 이미 있으므로 활용한다. `/health`의 고정 정상 응답만으로 게임의 상태까지 정상이라고 판단하지 않는다.

- [ ] CI에서 `npm ci`, 형식·타입 검사, 엔진·소켓 테스트, 프로덕션 E2E, 개발 모드 E2E를 자동 실행한다. 필요한 브라우저 설치 단계와 실패 trace 보관을 포함한다.
- [ ] 익명 방 생성·참가 시도와 WebSocket 메시지에 필요한 접속·빈도 제한을 정하고, 이미 있는 방 내부 제한과 중복되지 않게 적용한다.
- [ ] 공개 주소의 허용 Origin과, 프록시를 사용할 경우 실제 IP 판정 기준을 명시한다. Origin 검사를 사용자 인증으로 간주하지 않는다.
- [ ] 정상적인 3~6인 플레이는 유지하면서 반복 요청을 제한하는지 검증한다. 제한 응답이 한국어 안내로 이어지는지도 확인한다.
- [ ] 활성 방·참가자 수, 비정상 종료, 재접속 실패, 오류율을 확인할 최소 로그를 정한다. 비밀 미션 배정과 재접속 토큰은 로그에서 제외한다.
- [ ] 단일 서버를 대상으로 방 생성·종료를 반복하고 여러 방을 함께 실행해 메모리·응답 시간·타이머·방 해제를 측정한다. 첫 측정값을 바탕으로 공개 테스트 인원을 제한한다.
- [ ] 배포 설정, 상태 확인, 재시작으로 진행 중 게임이 사라지는 점, 장애 안내와 이전 버전 복귀 절차를 문서화한다.

**완료 기준:** CI가 깨끗한 체크아웃에서 통과한다. 운영 제한과 동시 접속 기준을 측정 결과로 설명할 수 있고, 배포·재시작·복귀 명령이 문서에 있다.

**산출물:** `.github/workflows/ci.yml`, `docs/operations.md`, `docs/load-check.md`. 구체적인 호스팅 서비스·도메인·비용은 아직 결정하지 않았다.

### 6. 소규모 외부 테스트

앞 단계에서 플레이를 막는 문제가 해결되고, 실행 환경이 정해지면 진행한다.

- [ ] 실제 HTTPS/WSS 주소에서 `/health`, 웹 로딩, 방 생성·코드 참가·초대 링크를 확인한다.

## 5. 다음 작업 시작 명령

아래 명령의 `/path/to/oddbid`를 실제 저장소 루트 경로로 바꾼다. 이미 설치된 환경에서 문서만 수정했다면 의존성 재설치와 전체 테스트를 반복할 필요는 없다.

```sh
cd /path/to/oddbid
git status --short --branch
git diff --stat
```

새 체크아웃 준비:

```sh
npm ci
npx playwright install chromium webkit
```

개발 실행:

```sh
npm run dev
```

변경 범위에 맞춰 검증:

```sh
npm run format:check
npm run typecheck
npm test
npm run test:e2e
```

`npm run test:e2e`는 빌드를 포함하며 별도 서버의 2568 포트를 사용한다. 소켓·브라우저 호환성이나 Vite 설정을 바꾼 경우 아래 검사도 실행한다. 실행 중인 개발 서버를 먼저 종료해 5173/2567 포트를 비워야 한다.

```sh
npm run test:dev
```

빌드 결과를 직접 확인하려면:

```sh
npm run build
npm start
```

기본 주소는 `http://localhost:2567`이다. 기존 개발 게임 서버도 2567을 사용하므로 함께 실행하려면 `PORT=2570 npm start`처럼 다른 포트를 지정한다.

## 6. 다음 작업에서 지킬 구현 기준

- 서버가 입찰·잔액·시간·미션·정산의 기준이다. 화면 표시만으로 낙찰 또는 차감을 확정하지 않는다.
- 참가자의 미션 배정은 서버의 비공개 상태와 본인 전용 메시지에 유지하고, 최종 결과 전 공개 스냅샷에 넣지 않는다.
- `apps/web/build/colyseus-browser.ts`의 SDK 0.18.4 WebSocket 보정은 이유 없이 제거하지 않는다. SDK 업데이트 시 필요성을 다시 검토하고 두 브라우저에서 연결·재접속을 확인한다.
- Vite의 게임 소켓 프록시를 모든 `/` 경로로 넓히지 않는다. 현재 설정은 HMR 소켓과 게임 소켓을 구분한다.
- 차콜·살구빛 주홍색과 부드럽고 선명한 제목, 둥근 카드·입력·버튼 체계를 유지한다. 사용자가 딱딱한 인상을 지적했으므로 과한 굵기, 날카로운 도장·해칭, 직각 패널로 되돌리지 않는다.
- 현재 작업 트리의 디자인을 유지하고, 작업 시작 시 다른 미커밋 변경이 있으면 덮어쓰거나 초기화하지 않는다. 테스트 결과와 실제 기기·운영 환경에서 아직 확인하지 못한 항목을 분리해 기록한다.
